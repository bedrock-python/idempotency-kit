# Project profile

## About

- What this repository is: `idempotency-kit`, an idempotency library for async Python applications, published on PyPI. An operation runs once per idempotency key, and a repeat call gets the stored result.
- Who uses it: asyncio services (HTTP APIs, background jobs, event consumers) that must not repeat an operation when a request or a message arrives again.
- Language, version and main frameworks: Python 3.11 and newer, asyncio only. Pydantic 2 is the one runtime dependency. Optional extras: `redis` (redis-py and orjson, for the Redis repository in `idempotency_kit/infra/storage/redis/`), `prometheus` (`idempotency_kit/infra/metrics/`) and `dishka` (Dishka providers in `idempotency_kit/dishka/`).
- Where the documentation lives: https://bedrock-python.github.io/idempotency-kit/, built with Zensical from `docs/` (`zensical.toml`). `docs.yml` deploys it on every push to `master`, not at release. `docs/agents.md` is the one-page reference for coding assistants.

## Commands

| Task | Command |
|---|---|
| Install dependencies | `uv sync --group dev` (`make install`). No extras are needed: the `test` group inside `dev` brings redis, orjson, dishka, prometheus-client, fakeredis and testcontainers. Hooks: `uv run pre-commit install --hook-type pre-commit --hook-type commit-msg`. |
| Format | `make fmt`: `uv run ruff format .`, then `uv run ruff check --fix .` |
| Lint and type-check | `make check`: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy idempotency_kit`. CI's lint job runs the same three. |
| Test | `make test-unit` (`uv run pytest -m unit`, no Docker). `make test-integration` (`uv run pytest -m integration`) needs Docker: it starts `redis:7-alpine` through testcontainers. CI runs `uv run pytest -m unit --cov=idempotency_kit --cov-report=xml` on Python 3.11, 3.12, 3.13 and 3.14, and `uv run pytest -m integration --cov=idempotency_kit --cov-report=xml --cov-fail-under=50` once. |
| Run locally | A library: nothing to run. The docs: `make docs-serve`. |
| Stop the local run | Ctrl+C in the terminal of `make docs-serve`. |

## Conventions

- Default branch: `master`. It changes only through a pull request, and its ruleset requires the `All checks passed` check (the last job of `ci.yml`). The pre-commit hook `no-commit-to-branch` refuses local commits to it.
- Issue tracker: GitHub Issues of this repository, with bug report and feature request forms and no blank issues. Refer to an issue as `#123`.
- Branch names: `<type>/<short-description>`, such as `feat/my-feature` (CONTRIBUTING.md).
- Commit messages: Conventional Commits, enforced by the `conventional-pre-commit` hook. A breaking change takes `!` (`feat!:`) or a `BREAKING CHANGE:` footer. Pull requests are squash-merged. The squash commit keeps the commit's title for a one-commit pull request and takes the pull request's title otherwise. Release-please reads that title, so both must be Conventional Commits.
- Language of pull request titles and descriptions: English.
- Where specs and design notes go: in the pull request description; the repository has no place for them.

## Boundaries

- `CHANGELOG.md` is generated by release-please. Never edit it by hand, and never add an `## [Unreleased]` section.
- The version lives in `idempotency_kit/__version__.py`, on the line marked `# x-release-please-version`, and in `.release-please-manifest.json`. Release-please bumps both. Never change them by hand.
- `docs/agents.md` is part of the public API: it changes in the same pull request as the API (CONTRIBUTING.md, "The agents page"). `docs/api_reference.md` is hand-written, not generated from docstrings, so an API change updates it too.
- Files from the engineering-assets hub (`AGENTS.md` explains how it works) include the copy-page files (`docs/assets/javascripts/copy-page.js`, `docs/assets/stylesheets/copy-page.css`, `overrides/main.html`, `scripts/emit_markdown.py`), `.github/workflows/docs.yml`, `.github/workflows/release-please.yml`, `.github/dependabot.yml`, `.editorconfig` and `CODE_OF_CONDUCT.md`. Change them in the hub; a change here makes the file this repository's own.
- Never publish to PyPI, push a tag or create a release by hand. Release-please creates the release and its `idempotency-kit-vX.Y.Z` tag, and `publish.yml` publishes it. Leave the manual run of `publish.yml` (`workflow_dispatch` with a `tag` input) to maintainers.

## Notes

- Releases: release-please opens its pull request with the workflow's own token (`release-please.yml` sets no `token`). So CI runs no jobs on that pull request, and the required check never reports. Close and reopen the release pull request to run CI, then merge it. `publish.yml` publishes to PyPI when the Release Please run on `master` completes and finds an `idempotency-kit-v*` tag on the commit. Only `feat`, `fix`, `perf` and `revert` commits reach the changelog. Before 1.0, a breaking change bumps the minor version (`bump-minor-pre-major`).
- Tests: the markers `unit` and `integration` come from the directory (`tests/unit/conftest.py`, `tests/integration/conftest.py`) under `--strict-markers`; do not add them by hand. Without Docker, the integration tests are skipped rather than failed. `docs/testing_conventions.md` sets the rest: names follow `test__subject__condition__expectedresult`, tests carry `# Arrange` / `# Act` / `# Assert` comments, and fixtures live only in `conftest.py`.
- Coverage: CI's unit run fails under 85% (`fail_under` in `[tool.coverage.report]`). That measure leaves out `dishka/`, `settings.py` and `infra/metrics/`. `make test` runs both suites and fails under 90%, but CI never runs it.
- Architecture (`docs/architecture.md`): `idempotency_kit/core/` holds the models, protocols, coordinator and the `async_idempotent` decorator, and imports only the standard library and Pydantic. `idempotency_kit/infra/` implements those protocols (the Redis repository, the Prometheus metrics) and depends on `core`, never the reverse.
- Code style (CONTRIBUTING.md): type hints on every function, tests included; Google-style docstrings on the public API only; lines up to 120 characters; double quotes; comments only for a non-obvious why.
